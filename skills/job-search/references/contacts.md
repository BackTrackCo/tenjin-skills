# Contacts (on request, Haiku subagent)

The first time the person asks, ask how many jobs with the question tool (`J ask contacts`: "5 jobs (Recommended)", "10 jobs", "Every job that passed review", or Other for a number). No answer means 5. Keep the answer as their `contact_count` rule (`J contacts count <n|all> --words "<their words>"`); later requests use it without asking, and the person can change it outside a batch. Never ask in an unattended turn. Free ways first, for each job:

0. Code first: the author of a post that led to the job is already a contact (the X handle, or the one email in the text), and with Tenjin `J contacts route` runs the router's people search for the requested jobs, with no subagent. A found person whose address does not name the job's city is dropped. Never open `profileUrl`; it is only shown to the person.
1. The free ways, the only Haiku step: the team page, talks, blog posts, GitHub, and LinkedIn profiles that appear in search results. Use a LinkedIn profile only as a link from a search result; never fetch a LinkedIn page, never sign in, never use the Y Combinator company page.

Each contact needs: a source link, how to reach them, and one thing they care about. `J ops` `contact` refuses a contact without them:
`{"op":"contact","key":"..","name":"..","title":"..","sourceUrl":"..","how":"..","cares":"..","channel":"x|linkedin|email|other"}`.
A likely person (for example the likely hiring manager from a team page that does not name them) is shown only when marked `"basis":"likely","notConfirmed":true`. Never guess a name or an address. If none is found, say so.

Messages are drafts: `J write-prompt --contacts <key,key>` gives an Opus call; the person edits and sends them.

## Example intros

For every contact whose record names a `channel` (an X handle, an email address, a LinkedIn profile or another public way), the round's one writer call (`J write-prompt --round`, `J write-result --round`) writes the example intros, together with the sheets and the leads. For one job alone: `J write-prompt --intros <key>`, then `J intros save <key> --result <file>`. An X or LinkedIn intro is under 300 characters; an email has a subject line and about 120 words at most; code checks the length per channel and refuses a contact with no channel. The intro is a draft the person sends themselves: never open LinkedIn or another never-automated site to send or read it, and never sign in. No consent gates it, and it is never held as `writing_needs_yes`. In an unattended run the intros are written and kept.

## Sending the intros

An intro is a draft. Nothing is sent without the rules below, and the skill never opens x.com, LinkedIn or another never-automated site to send or to read, and never signs in.

- **Email, through the Gmail connector.** Only the model can call the connector, so SKILL.md tells it which step to take; code decides what may go. An email goes only to an address the poster published in the post itself (an HN comment or an X post, alike; with a handle and an address in an X post the channel is email and the report still shows the DM link, with no second draft), kept only when code found it word for word in that post. An address from people search, a team page or any other source stays a draft the person sends (a `mailto:` link in the report). One email per address: none to an address the skill emailed, drafted or showed in the last 90 days, and the skill sends no follow-up email. The email carries the intro's subject and text from the person's own Gmail and no attachment.
- **By default, after a yes, in a batch.** When a round's email drafts are ready: `J email batch` lists them (the first batch asks the mode once: `J ask email-mode`, then `J email mode ask`, or `J consent record email` for the unattended mode). `J ask email` builds one question-tool call (up to 16 drafts as multi-select questions of 4 options each; with more, "Yes, send all N", "None" and "Other" for the numbers). `J email approve <ids> --skip-rest` records the yes per draft hash; the unticked drafts are not sent. `J email next` hands out one approved draft whose recipient passes the checks; send exactly that with the connector's send tool, then `J email sent <id> <message id>`.
- **Unattended, opt-in.** Off unless the person chose "Send without asking, within my rules": a separate `email` consent, bound to the rules hash, refused inside a batch, revoked with `J consent revoke email`, never granted by a rule or a lesson. With it, `J email next --unattended` hands out drafts with no per-batch yes, still only to published addresses, once per address, and within the person's rules (an excluded company, the fit floor). Each send gets a report line. The connector's tool also needs the person's own permission rule.
- **A connector that only makes drafts.** Record it with `J email connector drafts`: the batch becomes Gmail drafts through the connector's draft tool, the person presses Send in Gmail, and `J email sent <id> --drafted` records it. An unattended run makes the drafts and notifies once. **No connector:** `J email connector none`; show the text with the `mailto:` link, the person sends it, and `J email sent <id> --shown` records it.
- **X DMs and LinkedIn notes: the person sends.** The writer drafts the DM. Code gives the poster's profile link and the text to paste; whether X's DM link can carry the text is not verified, so none is built. The person presses Send. Reading X posts through the router's X search stays as it is: that is the supplier's API, not our browser.

## Finding the company before the people search
The employer's website names the right company, since a short name alone matches many. A job from a job board often has none, and that never stops the search. Before `J contacts route` searches for a job's people, code looks for the website: a link field in the job record (`record`), the routed posting's employer website field (`posting`), the company homepage link on a posting or board page code reads (`board_page`); with Tenjin, a company lookup by name or link (`company_lookup`, a routed need with the board link and the city as context, about 1.2 cents; its spec is fetched free first). Code checks the domain against the company name and the board's company name before it saves `employerWebsite` and its source. With no website found, the people search still runs by company name and city: a person from a different company is never recorded, a person whose company matches a known domain or the board's company name is a likely contact, and any other result is marked weak in the report. `J contacts route` prints every job it did not search (`notSearched`, with the reason), and the report says "not searched: <reason>"; "returned nothing" appears only when a search ran and came back empty. Never tell the person a search "returned nothing" when `J contacts route` said it did not search. The lookup returns one company object with no match score, so code trusts its bare `domain` only when its `name` or `legalName` matches the job's company name (or the board's), saves it as `employerWebsite` (never reading its registered address as the job's city), and keeps the company's LinkedIn page so a lead can match through its company page. A lead's company website is read by its host, never its path. A lead is marked weak when its last title has a sales or solutions word ("Field", "Solutions", "Sales", "Account"), when its headline names a different company than its last company, or when nothing confirms the company. The place filter matches a metro area, so a lead whose address does not name the city is dropped, and the report counts them ("2 found, 1 outside <city>").
